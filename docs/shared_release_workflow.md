# FE Core 与 fe-cli 共享维护工作流

维护规范修订：3；日期：2026-11-16。权威正文暂存于 fe-cli 仓库，供两个项目通过 AGENTS 引用。
修订 3 纳入维护者指定的固定目录和当前 Core 选择方式；运行部署验收状态仍按各次交付记录。
本文件规定协作、版本和发布要求；CLI 安装源和发布状态见[安装手册](installation.md)。
公共客户端不携带或发布服务器实现；本库操作不代表部署或升级服务器。

## 1. 产品与组件边界

- **fe-cli**：本机界面、因子 CSV、配置、SSH 提交/查询、下载校验、本机结果管理；不依赖 FE 才能安装和启动。
- **FE Core**：DSL、编译器、算子、执行、结果合同、导出/回读，以及其公共服务器部署包。
  公共包包含版本入口、环境和必要的数据适配/结果交付模块，与 Core 使用同一版本，不是第三个产品。
  Core 计算库与部署子模块可保持内部职责边界；计算库可独立安装和测试，不反向导入 CLI 或调度实现。
- **DA**：数据获取及其公开合同。当前磁盘适配器暂保留在 Core 部署职责内，替换时明确字段、单位、复权、日历与 PIT 归属。

当前 fe-cli 只保留客户端与通信合同；运行器、数据准备与部署器属于独立的私有后端。
CLI 只上传固定请求并调用获准服务器入口，不上传或动态下载后端实现。

Core 抽取先登记公开 API、依赖方向、包内原生构件、资源生命周期及独立安装验收，再移动代码。
模块位置变化不能悄悄改变数值、默认参数、字段映射或有效性语义。避免复制两份 Core 长期维护。
跨仓库任务明确各自写入范围；修改接口时同步生产者、消费者、兼容测试和文档。

## 2. 独立版本与兼容性

1. 只有两条独立产品版本线，均采用 `X.Y.Z` 规则：Core 延续自己的 `0.4.x → 0.5.x → 0.6.x`；
   CLI 的受管理版本从 `0.1.0` 起步，独立演进到 `1.0.0`。两者不要求同号、同步升级或同时发布。
   公共服务器部署包就是 FE Core，其版本沿用 Core；平台、环境构建标识和摘要不是第三套产品版本。
2. 每个产品单独保留版本、Git SHA、工件摘要、日志和验收证据；依靠兼容性清单关联 CLI/Core 组合。
   清单记录 CLI 版本、支持/验收过的 Core 版本、协议/schema、平台/节点和证据，范围由测试决定，
   不能从数字相近推断兼容。外部 DA、Python、Polars 保持上游版本；协议、数据快照和计算身份另记。
3. 稳定版本：不兼容的公开合同变化升 MAJOR；兼容功能增加升 MINOR；兼容修复升 PATCH。
   文档或重构提交不自动触发版本发布。`0.x` 阶段明确使用 MINOR 承载破坏性变化，PATCH 保持兼容，
   日志仍必须标出破坏性变化；达到稳定合同与交付条件后再发布 `1.0.0`。
4. 各仓库统一自身包元数据和标签写法：如 CLI `0.1.0` / `0.1.0rc1`，Core `0.6.0` / `0.6.0rc1`，
   各自标签为 `v<本产品版本>`。同一分发入口需注明产品名，不能将 CLI 版本当成 Core 版本。
   上述号码说明版本线，不代表相应工件已发布。
5. “公开合同”包括 Core API/DSL、默认参数、数值与有效性语义、请求/结果协议、CSV/配置/schema、
   CLI 稳定命令与退出码、支持的 Python/平台、旧结果可读性。界面小调整不自动视为破坏性变化。
6. 修复错误实现可以按 PATCH 发布，但只要结果可能改变，就必须说明影响范围、旧值是否需要重算及证据。
   主动改变已承诺的数学口径、单位、缺失/PIT、预热或递归初始化，按破坏性变化处理。
   纯性能优化必须在预先定义的数值容差内验证，不能通过临时放宽容差掩盖回归。
7. 表达式相同不等于计算相同。计算/缓存身份必须考虑引擎与原生实现、编译器、数据快照和语义合同；
   更换计算语义不得覆盖旧值或直接拼接旧结果。包入口文件摘要不能代表完整 Core 实现。
8. 支持旧结果读取与支持旧任务继续计算分别声明；依协议/schema/能力判断兼容，不能仅凭版本号相同放行，
   也不能仅凭版本号不同拒绝读取。历史请求、回执、目录及工件不得为整理版本规则而重写。

## 3. 日常迭代与记录

1. 开工核对分支、HEAD、dirty 文件和正在进行的其他任务；保留既有修改，明确本次范围与可验收结果。
2. 先判断是否改变公开合同、数值、依赖、持久化或部署。涉及跨层边界时，先记简短接口/决策，再实现。
3. 小步实现，补充验证行为的测试。日常用目标模块验证；按继承的成本规则安排全量测试，避免重复全量运行。
4. 有用户可见影响的变更立即登记到 `CHANGELOG.md` 的 `Unreleased`，采用
   Added / Changed / Fixed / Deprecated / Removed / Security 分类。描述行为和影响，不粘贴 Git 日志。
5. 详细工程记录保留复现条件、关键决策、验证命令/结果、平台/节点/真实 Job ID、限制和未验收项。
   README 近期迭代只给简短摘要与详情链接；安装、默认行为或配置变化同步用户手册。
6. 一个可验收检查点形成独立本地 commit，交付时报告摘要。commit 不等于发布，不要求每次 bump。
   未发布代码用 commit 与 `Unreleased` 区分；不得把本地验证描述为已部署版本的能力。
7. 各产品发布负责人在冻结时确定该产品目标版本，核对相关仓库和兼容声明；不由各代理自行抢占版本号。
   一方单独迭代不强制另一方 bump；跨产品合同变化才协调双方发布与迁移顺序。

工程记录至少包含：日期、范围/问题、变化、兼容及数值影响、验证证据、未验收范围、对应提交。
发布日志另加：版本、发布日期、组件 SHA/工件摘要、安装/升级步骤、迁移与回滚方式、已知问题。

## 4. 发布、安装、升级与回滚

### 发布前置条件

**服务器来源（维护者要求，2026-11-16）：** 必须先将本机修改推送远端并形成指定版本发布；服务器仅从远端拉取该发布版本及经摘要核验的工件。禁止服务器现场改源码、上传本地源码补丁或安装未发布诊断版本。拉取时固定发布标签与提交，不追随开发分支 HEAD；发布和服务器安装分别授权、分别记录。

- 明确本次支持的 CLI/Core 组合、请求/结果协议、配置/schema、Python/OS/ABI、依赖及节点。
  任何“全部通过”的声明必须限定范围。一个节点或源码环境通过，不能代替其他节点或安装包验证。
- 从固定提交构建，检查工作树与构建上下文，排除临时文件、凭据、私有数据和未登记修改。
  必要时使用干净隔离构建目录，不清理他人的工作树来凑干净状态。
- 本次有变更的产品从自身 wheel/发布包在独立环境安装；另一方复用固定的兼容工件联调，无需重建或重发。
  避免从源码目录成功导入掩盖漏打包。
  Core 验证原生构件/ABI、代表计算、有效性和导出/回读；CLI 验证初始化、配置、历史读取与用户主路径。
- 联调覆盖请求→调度→Core/数据→结果包→下载校验→本机回执，并保留预期失败、断连和重复取回证据。
  只有真实任务与真实产物才能支持真实运行声明；doctor、模拟、合成测试分别记账。

### 固定工件与发布清单

每个正式发布均需版本日志、固定源码提交、不可变工件、摘要及兼容说明；PATCH/MINOR 也不例外。
以下是目标清单要求，现有 `release.json` 自动化尚未实现全部字段：

| 身份 | 最低记录 |
| --- | --- |
| 本产品 | 产品名、独立版本、清单 schema、构建时间；渠道推广状态另记 |
| CLI 或 Core 工件 | 对应 Git SHA、wheel/源码包 SHA256；两产品不强制同时构建 |
| Core 公共部署 | 沿用 Core 版本，记录 runner/适配代码、依赖锁或离线库存、原生构件清单/ABI |
| 兼容范围 | Python/平台、协议/schema、已验证节点与组合、已知不支持项 |
| 证据与运维 | 测试/真实任务记录、安装与升级文档、迁移说明、回退版本 |

同一版本、平台和构建身份的已发布工件不可换内容；修复发布新版本，不覆盖历史文件或修改已有标签。
平台工件各有标签与摘要，不另起一套产品版本。依赖或原生环境改变也必须登记新的构建身份及验证。
每个产品只维护一个自身版本的权威来源，运行时版本、构建元数据与清单由其派生或校验一致。
服务器入口或适配代码变更属于 Core 发布内容，按影响升级 Core；不以独立的运行包产品版本绕过记录。

若使用 `X.Y.Zrc1`，正式 `X.Y.Z` 的包元数据不同，必须另构建并验收正式工件，不能改名当正式包。
最终版本工件先在候选渠道/环境验收，再将**同一组摘要对应的工件**推广为正式渠道，不能推广时重建。
候选/正式渠道、推广时间、执行维护者及回退操作写入独立推广记录，关联不可变发布清单的摘要；
不能为改变渠道状态而改写已被任务固定的 `release.json`，否则会改变其摘要。
Git tag、包、文档与发布清单必须指向对应提交；“已构建”“已部署”“已推广”分别记录。

### 安装和使用文档

面向成员提供 CLI 安装与用户手册，面向维护者另提供 Core 独立安装和公共环境维护说明。
每次发布至少核对：支持平台/Python、真实可用下载源、固定版本安装、摘要、首次配置、因子库、
节点/日期/资源、首次 run/results、常见失败、升级/回退、旧 workspace 保留及支持边界。
成员安装 CLI 不应隐式安装 Core、下载行情或编译原生库；默认文档采用发布工件，不要求克隆两个源码仓库。
发布入口尚未可用时明确只支持源码安装，不编造下载地址、包索引或“一键安装已完成”。
升级提示区分 CLI 更新和服务器 Core 版本切换，分别展示当前/目标版本及兼容性，不在运行中静默切换。

### 公共部署与升级

维护者当前选择 `/public/fe-core` 源码及 `/public/fe-core-env` 环境两个固定目录，
后续在维护窗口复用，不逐版本累积完整环境；既有实验目录保留原名和摘要，不自动删除。
虚拟环境在最终绝对路径创建，验收后原子发布就绪清单；不假设虚拟环境可从临时路径直接改名搬迁。
共享代码只读运行，缓存及临时数据留在个人/作业可写位置，密钥和私有数据不进入公共发布包。
新初始化配置选择当前 Core，不要求固定 SHA 或每次升级后重新 configure-run。
请求冻结所选路径和 current 策略，服务器在作业实际启动时解析一次清单，校验完整安装身份，
把实际版本、提交、清单和 wheel 摘要记录到结果；原请求不因解析被改写。
旧固定 SHA 配置和请求继续严格匹配，不自动改写历史身份。更新前暂停新提交，
确认引用两目录的排队与运行任务已结束；不得覆盖计算中的代码或环境，失败不标记就绪。
服务器发布、远端仓库写入和正式推广沿会话已有授权执行；本规范本身不代表已获得执行授权。
服务器安装来源必须是已发布的远端源码标签/提交和同一发布的工件，先核对身份再取得并安装。
不得用本地未发布源码或诊断补丁覆盖现场；CLI 更新使用 GitHub Release 与 `fe-cli --update`，
不会替成员发布或部署 Core。Core 的修改、发布与服务器升级须在各自任务范围内处理。

MAJOR 及任何破坏性升级，发布前额外完成：迁移文档、旧客户端/旧数据读取验证、升级演练、
结果变化与重算计划、回滚演练及支持窗口声明。必要迁移采用显式入口，先备份，再验证；
不得自动删除/重建已有环境、清空 CSV/值目录，或为通过校验改写旧回执。
回滚分别处理客户端版本、服务器新任务入口和配置/schema；只回退代码不保证已迁移数据可回退。
历史结果继续保留身份；停用或清理旧版本前，核对运行任务、历史引用、留存与维护者授权。

## 5. 接入工程约束

两项目的 AGENTS 保持简短，引用同一规范，避免复制长文后各自漂移。本地当前可用引用：

```markdown
## FE 共享维护与发布

- 开始版本、接口、依赖、安装或部署相关任务前，阅读
  `docs/shared_release_workflow.md`（修订 3）。
- Core 与 CLI 独立编号；CLI 从 0.1.0 起步，公共部署包沿用 Core 版本，以兼容清单关联双方。
- 保留各产品提交、工件、协议与数值身份；不重写历史发布，不为另一产品迭代强制 bump。
- 日常变更登记 Unreleased、验证并形成检查点提交；提交不自动等于发布或部署。
- 用户可见变化同步日志与手册；数值/持久化/破坏性变化明确迁移及回滚。
- 交付报告版本/提交、验证范围、已部署范围和未验收项；远端写入遵循已有授权。
```

各工作区使用已固定修订的仓库链接或随仓库提供的规范副本。
若必须复制正文，记录维护规范修订及来源摘要，修改时同步两项目，禁止形成两个权威版本。

## 6. 当前客户端边界

- 最新正式 CLI 为维护者确认的 `0.1.1`；安装源及推广状态见[安装手册](installation.md)。
- 旧实验 CLI `0.5.4` 排序高于 `0.1.0`，首次迁移必须显式选择目标工件并保留 workspace。
- 首次 init 自动补标准解释器、数据位置和固定入口配置，配置操作不验证授权或部署状态。
  新配置无需固定摘要，实际作业启动后记录当前 Core 身份；自定义及旧固定配置保留。
  旧代码上传模式不再支持。
- 服务器授权由 SSH 和服务器权限执行，客户端参数校验不替代服务器访问控制。
- 后端维护及真实数据验收独立记录；本轮客户端发布不宣称任何节点或新 Core 组合真实验收通过。
- CLI 维护者负责客户端、兼容声明与成员手册；后端维护者负责服务实现及服务器发布。

修订 2 按用户澄清改为两个独立版本线、Core 公共部署归属及兼容性关联，未改变软件包或服务器。
